# 变更产物链

`.changes/` 下每个目录是一条**变更产物链**：一次改动的三层产物，逐层回答"要解决什么""系统应当怎样""这次怎么做"。链是这次改动的历史快照，不是当前行为的权威——当前行为只在文档与源码里。

## 目录与命名

一条链是 `.changes/<slug>/` 下按进度长出的文件（见下节），只允许 `intent.md`、`spec.md`、`plan.md` 三个。`<slug>` 是连字符分隔的小写短语，描述改动本身，不编号。

完成的链移到 `.changes/archive/YYYY-MM-DD-v{n}-<slug>/`，日期用归档当天，`v{n}` 当天从 1 递增，同一天的链按它排先后。根目录只放在制的链——产物不带状态行，"在制"与"已完成"只能靠位置区分。

## 层数按边界浮动

缺层合法，跳层不合法。改动跨得越远，链越长。

- **`intent.md`** —— 默认起点：要解决的问题、期望结果、约束、未决问题。
- **`spec.md`** —— 只在改动**改变系统行为**或**越过既有策略边界**时落：系统行为、数据流、受影响的系统、策略冲突。
- **`plan.md`** —— 改动落地时落：动哪些文件、什么顺序、怎么证明。它同时是执行清单与评审对照的基线。

闸门强制的只有一条：`spec.md` 一旦存在，就必须有 `intent.md`。其余都是约定，不是闸门——`plan.md` 可以单独存在（小改动），`intent.md` 加 `plan.md` 而不写 `spec.md` 也合法（不改变系统行为的简化）。

## 未决问题

还没定下来的事写进 `intent.md`，用可机械识别的标记：

```text
[NEEDS CLARIFICATION: 第三方理赔员是否也要能看到？]
```

`spec.md` 一旦存在，`intent.md` 里不得遗留这样的标记——每一处要么已被回答，要么被显式结转并写明由谁决定。

## 每层的必备章节

只有这些章节必须存在，其余自由。首行是三份产物各自的机器可读标识。

- `intent.md` —— `# Intent: <标题>`，必备 `## Problem`。
- `spec.md` —— `# Spec: <标题>`，必备 `## Behavior`、`## Alternatives considered`、`## Areas of concern`。
- `plan.md` —— `# Plan: <标题>`，必备 `## Files`、`## Proof`。

`## Behavior` 要给出可校验的门，例如"引入新概念或新依赖必须给出当前消费者证据"；不通过就写明为什么非引入不可。`## Areas of concern` 允许写"无"——"没有冲突"与"没检查过"必须能区分。`## Alternatives considered` 记录这次设计打败了谁，否则同一个方案会被重新争论一遍。

## 冻结

链在改动进行中可以反复改；合并后冻结。不要为了让一条已完成的链跟上后续改动而回头修它——它记录的是当时决定要怎样，不是现在怎样。决策被推翻时在新链里说明，不回头改旧链；链之间的取代关系不记录。

冻结不使它失去用处：`spec.md` 的 `## Alternatives considered` 是那次设计打败了谁的唯一记录。**要重新争论一个既有决定时，去 `.changes/archive/` 里搜**，那是这类理由唯一的所在。

## 什么时候写

每个非平凡改动至少一条链。判据是：改变了行为、架构、跨文件或跨模块的约定、流程或工具、测试策略、磁盘或网络格式，或任何维护者可能重新审视的决定。

## 推迟的发现

一次改动常会顺手发现别处的缺口，而那个缺口不该由这次改动顺手修掉——它会让链变大、评审变糊，也把两件事塞进一次改动。

它的落点是一条**只含 `intent.md` 的链**，写在 `.changes/<slug>/`，留在根目录直到被解决或被放弃：解决时补上后续层再归档，不做了就删掉。

它不随发现它的那条链一起归档。归档即冻结，没人会再读到冻结的 `plan.md`——那条链关闭之前，它的发现必须先长成自己的链。

## 归档

```sh
n=$(find .changes/archive -maxdepth 1 -name "$(date +%F)-v*" | wc -l)
git mv .changes/<slug> ".changes/archive/$(date +%F)-v$((n + 1))-<slug>"
```

归档的链不再改动。闸门只校验 `archive/` 下的路径形状，不校验内容格式——格式会演进，冻结的历史不该被追着改。
