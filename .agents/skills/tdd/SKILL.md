# 测试驱动开发（TDD）

TDD 是「红 → 绿」循环。本技能是让这个循环产出值得保留的测试的参照：什么是好测试、测试放在哪、反模式、以及循环的规则。每一节在每一轮循环里都适用：在循环前和循环中查阅它们，而不是循环之后。

在探索代码库时，先读项目架构文档，让测试名称和接口词汇与项目的领域语言一致，并尊重你所触及区域的既有决策。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变；测试不应该。一个好测试读起来像一份规格说明："user can checkout with valid cart" 精确地告诉你存在什么能力，而且它能经受住重构，因为它不关心内部结构。

参见 [tests.md](tests.md) 中的示例和 [mocking.md](mocking.md) 中的 mock 指南。

## 接缝：测试放在哪里

**接缝（seam）** 是你进行测试的公共边界：你在此观察行为而不深入内部。测试活在接缝上，绝不对着内部。

**只在预先商定的接缝上测试。** 在写任何测试之前，写下被测的接缝并与用户确认。不在未确认的接缝上写测试。你无法测试一切，所以提前商定接缝，就是让测试精力落在关键路径和复杂逻辑上，而不是每一个边界情况。

要问："公共接口是什么，我们应该测试哪些接缝？"

当接口本身的形态存疑（模块该多深、接缝属于哪里、接口应该暴露什么）时，先读项目的架构文档与相关 `spec.md`，用它们的模块、接口、接缝词汇对齐；它们是用来查阅的参照，不是要运行的一次会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（直接查数据库而不是用接口）。标志：重构时测试挂了，但行为没变。
- **同义反复**：断言用代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`，一个用同样方式手工推导的快照，一个断言等于自身的常量），于是它天然通过，永远不可能与代码不一致。期望值必须来自独立的真相来源：一个已知正确的字面量、一个演算过的例子、规格说明。
- **水平切片**：先写完所有测试，再写所有实现。批量测试验证的是 _想象出来的_ 行为：你测试的是事物的 _形态_ 而非面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁定了测试结构。改为按 **垂直切片** 工作：一个测试 → 一个实现 → 重复，每个测试都是一发 **曳光弹**，回应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写足以让它通过的代码。不要预想未来的测试，也不要添加投机性的功能。
- **一次一个切片。** 每轮循环一个接缝、一个测试、一个最小实现。
- **重构不属于循环。** 它属于评审阶段（见 [`code-review`](../code-review/SKILL.md) 技能），而不是红 → 绿的实现循环。
