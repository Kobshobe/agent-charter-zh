# 寻找简化

把"找点东西简化"这类宽泛请求，变成有证据支撑的简化改动，真正删除或折叠已有的表面。它是指导，不是清单：跟着代码走，保持判断，宁要少数被证明的候选，不要一堆单薄的猜测。

## 从仓库上下文开始

- 读 [`AGENTS.md`](../../../AGENTS.md) 的约定，含"测试描述行为，而不是正确性"一条。
- 判定核心代码之前先看项目的架构文档；与既有模块划分或模型相冲突的简化需要额外证据。
- 用变更链理解**有意为之**的架构：`spec.md` 的 `## Alternatives considered` 记着当时打败了谁。完成的链在 `.changes/archive/`，**已有设计的理由只在那里**，所以要搜归档，不要只看在制目录。删除一条被记录过的边界，需要打败那条记录在案的理由，而不只是引用"优先依赖"的政策。

## 什么算强候选

一个强简化会删除、折叠或降级真实存在的东西，并有清楚证据表明当前设计的花费大于收益：

- 某个公开方法、事件、配置项、通知、辅助函数、模块或事件，**没有生产消费者**。
- 只有测试或文档在用它，而它们钉住的行为并不承重。
- 两份表示镜像同一个事实。
- 一个边界层的方法每个实现都必须支持，却没有消费者用。
- 一个独立模块只为测试或演示而存在，却带来发布或依赖开销。
- 某个特性实现了投机式通用化，没有产品负责人。
- 一段不变量、回滚路径或特殊测试，只为保护一个没人用的接口而存在。
- 手搓代码重新实现了某个**维护良好的依赖**已提供的东西，替换能同时删掉实现与它的专属测试。
- 简化后行为略有不同，但新行为仍合理且更好解释。

单薄的候选通常不够起一条链：删一个错别字、跑一次死代码扫描、或没有调用点证据地说"这看起来复杂"。

## 广泛调研

当用户要广度或候选很多时，用并行子代理，每个给一个领域并要求证据而非猜测。若没有子代理，自己模拟同样的广度。不要让第一个好候选终止调研。

从最大的生产代码增量开始。一次停在显眼未用符号的审计，会漏掉那些重复的生命周期或防御机制承载大部分成本的文件。

## 审计信任与生命周期边界

对每个防御性拷贝、冻结、校验器与回调捕获，说清值从哪来、下一个拥有者是谁。**同进程的类型化调用通常借用只读值**；解析器、配置加载、队列、外部 JSON、持久文件、worker、进程与网络解码器则拥有或校验它们的数据。围绕恶意 getter、伪造对象、回调替换或交接后修改构建的测试，是"契约可能投机的证据"，不是保留它的自动理由。

对复杂异步代码，画所有权图，把每个哨兵、就绪信号、取消路径、释放器与状态标志映射到一个不同的拥有者或转移。当多个机制镜像同一个存活或结算事实时，提出一个事务或生命周期控制器。

## 手搓还是依赖

引入依赖是合法的简化手段。调研时对协议解析器、帧、重试与退避循环、glob、diff 引擎这类基础设施问：维护良好的依赖或语言内建是否已经做了这件事？证明依赖替换候选时，还要看依赖的健康度与传递足迹，并优先内建；算净删除量（实现加专属测试加文档，减去剩下的胶水）。

## 证明或否决每个候选

对每个符号或行为，先分类消费者：

- 生产语料：源码、入口配置、运行时脚本与加载路径。
- 非生产语料：测试、文档、变更链、快照、生成的期望输出、注释。
- 模糊语料：可能是产品冒烟路径的示例与脚本；先看用法再分类。

先用搜索，再读调用点。静态分析工具可以帮助，但不能替代对公开接口、动态事件名、测试、文档与加载路径的理解。

否决或降级一个候选的条件：

- 存在生产调用方，简化会变成特性决策而非清理。
- 该接口由一条变更链的 `spec.md` 或来之不易的防御模式明确辩护，而新证据没有打败那个理由。
- 删除会带来无关改动，却没有真正减少公开接口或必需行为。
- 想法正确但很小。改用一条针对性的 TODO/FIXME/XXX，按紧迫度语义标注。

## 写 intent

在 `.changes/<slug>/intent.md` 里写这次简化的意图，遵循 [`changes/README.md`](../../../.changes/README.md)。段落一段一物理行。

- 首行 `# Intent: <面向动作的标题>`。
- `## Problem`：点名当前接口，引用相关文件，陈述消费者证据，把生产调用方与测试和文档分开。
- 其余章节自由，但要让实现者能照着判断该删到什么程度，并把最强的反论讲清楚。

简化若改变系统行为或越过既有约定，链要补上 `spec.md`。要具体到实现者能照着走，避免"简化这个模块"这种空洞意图。

"加了又删"是常见的完整移除案例：只有当那个特性已从生产代码、配置、schema、持久或线上格式、迁移与兼容行为里全部消失，且没有测试把它当作受支持行为时，才算移除完成。

## 行内 TODO

行内 TODO/FIXME/XXX 只用于小型、局部、明显有用但**不是持久设计决策**的清理：

- 用一个稳定的标签点出坏味道，如 `TODO(双重默认)`。
- 说明为什么可以安全重访、什么动作会简化它。
- 不要为投机式抱怨或需要起一条链的行为加 TODO。

## 校验与 PR 卫生

纯文档的工作至少跑 `python3 .agents/scripts/check_docs.py` 与 `git diff --check`。打开或更新 PR 时，总结采纳与放弃的候选、调研了哪些主要区域、有意排除了什么、跑了哪些检查。
