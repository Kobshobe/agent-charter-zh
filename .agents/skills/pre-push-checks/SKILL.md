# 推送前检查

在推送前，只跑**一次**覆盖本次改动的最小证据集。唯一的顺序例外是叠层 PR 的同步发布：它可能在本地校验之前就重写了分支，所以同步之后必须立即补校验。Git 钩子是刻意窄的；覆盖完整的 CI 属于远端，不属于本地。

## 确定本次改动

1. 确认工作区与分支。

```sh
git status --short --branch
git rev-parse --show-toplevel
```

2. 相对**已核实的远端基线**查看完整改动范围。不要猜基线：从当前远端或叠层状态里取。

```sh
git fetch origin <基线分支>
git diff --stat origin/<基线分支>...HEAD
git diff origin/<基线分支>...HEAD
```

合并过基线之后，重新跑一次范围报告，重新判断哪些行为可能受影响，只重跑因这次合并而失效的检查。

## 按改动面选证据

除钩子之外没有普适的本地基线。每个行为改动都要有**最窄的、能因它回归而失败的**测试或专用检查；只有当改动确实触达更广的面时才加更广的检查。

- **代码行为**：跑拥有该行为的测试文件或聚焦的测试用例名。当共享约定变化时，补跑相邻模块的测试。
- **文档、变更链、生成的目录或与文档关联的注释**：跑 `python3 .agents/scripts/check_docs.py`。
- **对外可见的输出**（接口、命令、界面、日志）：跑拥有该输出的聚焦测试或可运行的演示场景。
- **清单、公开导出、构建配置、入口脚本**：跑构建与相应的依赖和打包检查。
- **真实外部服务行为**：在有凭据时跑对应的集成目标；绝不打印密钥。

不要因为"接下来要提交"就手动重复一个已经通过的检查。

## 完整本地演练

只在三种情况下跑完整的本地近似：用户明确要求、正在诊断一次 CI 失败、或改动横跨整个仓库以至于没有可信的更窄集合。命令清单以当前工作流与脚本为准，不要凭记忆重建。

## 保护重写历史的推送

允许对独立分支与叠层分支 rebase（包括评审之后）。重写前先 fetch 远端分支并记录它的确切 OID，用 `--force-with-lease=<分支>:<观察到的 OID>` 发布，这样并发的远端更新会中止推送。**绝不使用裸 `--force`。**

任何重写推送之后，都要重新 fetch 活的分支头，并重新核对未解决的评审线程、批准、可合并性与检查状态。重写之前的提交哈希与行内评论锚点都不再是当前证据。

## 处理失败

推送前若相关检查失败，停下，修复或解释阻塞点。不要"先推上去看看 CI 是不是不一样"。

如果失败看起来与环境相关，证明它：记录确切命令、失败的测试、平台特有的差异；先确认不依赖平台的那部分证据；当检查是必需的时候，优先修跨平台的不确定性。只有在用户明确要求或同意时才绕过本地钩子，并如实报告失败内容与为什么 CI 预期会不同。

## 推送流程

1. 跑一次选定的相关检查。
2. 正常提交；若提交前的自动修复改动了文件，先检查它们再继续。
3. 正常推送，或对已授权的重写分支使用精确的 lease。
4. 核对远端 ref 与本地 `HEAD` 一致。

```sh
git rev-parse HEAD origin/$(git branch --show-current)
```

对 GitHub PR，推送后查看远端 CI：

```sh
gh pr checks
```

把待定的检查如实报为待定；在归因给分支或环境之前先看失败内容。当 `gh pr checks` 报"没有检查"而该提交确实存在时，先查可合并性再怀疑推送或基础设施。

叠层分支的落地用 [`merging-stacked-prs`](../merging-stacked-prs/SKILL.md)。
