# 文字标准

写到能保住约定为止，然后删掉推理过程、重复与装饰。**约定**是调用方、被调方、实现者、生产者或消费者所依赖的义务、不变量、前置、后置或兼容承诺。本技能拥有编辑判断与必需的覆盖；放置、字数与闸门用 [`doc-standards`](../doc-standards/SKILL.md)，推理过程泄漏用 [`trim-cot-leakage`](../trim-cot-leakage/SKILL.md)。它是指导，不是脚本。

把"约定、边界、形状、表面、接缝、闸门、词汇表"当作**使用前先检查**的词，而不是禁词：先问是否有更确切的说法能更好地陈述事实。当一个词命名了确切的、技术上的对象（包括调用方与被调方约定、安全与进程边界）时就保留它。

注释描述代码表达不了的不显然约定或理由；它不复述代码已经隐含的东西。

## 输入与排除

要求一个显式的范围。缺失时就报告所需输入并停止；不要推断成全仓库范围，也不要开始访谈。

模式取自动或交互，默认自动。只在用户明确要求提问或校准时才进交互模式。模式控制提问，不控制写权限：评审与审计任务只报告不改；明确要求写、修、精简的任务才应用清晰的改动。

总是排除第三方 vendor 目录与 `.changes/archive/`（冻结快照）。生成的目录、快照与夹具是派生物：先改拥有的源或场景，再重生成。

## 保住完整的命题

编辑前先识别段落里的每个命题，保留下每一条相关的：

- 动作主体与动作；
- 条件、时序与顺序；
- 情态（必须、可以、绝不）；
- 负面保证与例外；
- 所有权、副作用、失败模式与后果。

只有在每个事实子句都存活、且结果更清楚时，才删形容词、重复与叙述。**字数更少本身不是改进。**

在使用点保留完整的局部约定：调用方或维护者在那里需要的行为、失败、所有权与后果。架构、理由、算法、历史与扩展示例，激进地链接到拥有它的文档。一个解释只有一个归属处；关键约定事实可以在本地重复。

当省略某个不显然的理由可能合理导致误用或错误简化时，保留它；否则陈述后果并链接理由。

## 按位置要求覆盖

这不是单向的缩短。当代码、类型与结构不能传达下面的必需约定时，要补写或恢复。局部已经显然时不要加注释。

- **公开接口注释**：记录调用方可见的返回区别、抛出或拒绝、副作用、所有权、时序、取消与持久性。
- **内部注释**：为非局部的结构与显然复杂的局部结构定位，包括不变量、竞争顺序、所有权、安全边界与意外的失败行为。删掉控制流叙述与代码复述。
- **模块注释**：说明模块的角色、依赖、职责与不显然的架构选择，并链接架构选择。
- **测试**：只解释不显然的测试设计——为什么需要某个夹具、断言、平台适配、真实入口或间接观察。删掉走查与清单。
- **操作指南**：包含前置、必需动作、真实入口、可观察验证与简洁警告。
- **README**：包含消费者约定：配置、语义、失败、限制、扩展点与对外可见效果。引用由该模块拥有的稳定可见文本；链接生成的目录与跨模块拥有者。
- **变更链**：保留独特理由、机制、替代方案、后果与验证证据。进行中的链可用将来时；合并后冻结，不再回填。
- **事故复盘**：保留事故序列、证据、因果链、影响与预防。删掉不建立因果的重复说服或实现细节。
- **技能与代理指令**：陈述行为护栏与显式范围限制（如"是指导，不是脚本或清单"），保持工作流简洁并链接事实来源。
- **示例与配置注释**：解释访问限制、不显然的接线或加载顺序、安全立场、重放行为、例外与可能的误用；不要叙述配置已经展示的条目。
- **提示词与可见字符串**：把措辞当作行为。检查生成的输出并跑行为校验，或说明为什么没有快照适用。
- **诊断信息**：点名失败的对象或路径、被违反的规则、以及不显然时的纠正方式；删掉内部执行叙述。

保留可搜索的机制名与有意义的强调；只规范化装饰性强调。

## 工作流

1. 确认范围、模式、当前分支或 PR 基线与适用的 AGENTS.md。不要看无关分支。
2. 判定一段文字前，先读 [`doc-standard.md`](../../references/doc-standard.md) 与拥有它的代码或文档。
3. 检查被请求的范围，而不只是最大的文件。用搜索与字数找候选，再逐段语义判断。
4. 把每个候选分类为：保留、补写、精简、恢复、重组、推迟。只在任务授权时应用清晰的改动；不要为凑删除目标而制造改动。
5. 先改拥有者，再改派生物。学到一条新规则后重查类似的段落。
6. 跑最窄的相关检查、文档闸门 `python3 .agents/scripts/check_docs.py` 与 `git diff --check`，并验证最终 diff 里没有 vendor 路径。
7. 报告检查过的范围、清晰的改动、有意保留、推迟的案例与真正跑过的检查。

## 边界情形

只有至少两个版本都满足完整命题规则、却在被接受的原则之间取舍时，才算边界情形。在自动模式下应用清晰的改动并报告真正边界的情形，不要提问；不要为了推进而弱化命题。在交互模式下，把类似的段落归到同一原则下，给两三个可行版本、推荐一个、并说明事实或结构上的差别；不要给更差的干扰项。
